# Lesson 58: Automated AI Security Patches Breaking Container Linting Standards (Hadolint / Super-Linter)

### Context
Automated vulnerability scanning and AI bot PR generation (Aikido Security SAST/Container checks) targeting Dockerfile binary integrity in `pymc-marketing-mcp`.

### What happened
An automated AI bot opened PR #23 (`[Aikido] AI Fix for The binary integrity check is missing in the Dockerfile...`). The bot modified `Dockerfile` by adding an inline shell pipeline to download and verify checksums (`curl ... | sha256sum -c - && ...`). When the PR was tested against repository CI, Super-Linter and Hadolint failed on multiple container quality rules.

### Observable symptom
```text
Super-Linter Run / Lint Code Base
DOCKERFILE_HADOLINT errors found in Dockerfile:
  DL4006: Set the SHELL option -o pipefail before RUN with a pipe in it
  DL3008: Pin versions in apt-get install
  DL3013: Pin versions in pip
  SC2015: Note that A && B || C is not if-then-else
Result: CI FAILED on PR #23
```

### Impact
Automated bots created red CI builds that could have broken container image builds, introduced pipefail security vulnerabilities in production Dockerfiles, and distracted maintainers from real architectural security.

### Incorrect assumption
Assumed that automated AI security fixes generated by third-party SAST tools automatically comply with best-practice container linting standards and POSIX shell invariants.

### Root cause
**Confirmed**. The automated AI patch generator wrote naive bash one-liners (`curl ... | sha256sum -c -`) without setting `SHELL ["/bin/bash", "-o", "pipefail", "-c"]` (Hadolint rule `DL4006`), pinned no versions, and used unsafe compound shell operators. Furthermore, the bot failed to recognize that the existing multi-stage build already verifies cryptographic integrity via `Cargo.lock` and `uv.lock`.

### Why the architecture allowed it
External security bots were granted permission to open PRs against the repository without requiring local pre-commit hooks or local Hadolint validation before PR submission.

### Fix
1. Evaluated PR #23 against the repository's strict CI quality gates.
2. Rejected and closed PR #23 with a clear, diagnostic post-mortem comment explaining the Hadolint failures (`DL4006`, `DL3008`, `DL3013`, `SC2015`).
3. Retained the declarative multi-stage build architecture where Rust binaries are compiled from source with verified Cargo crate checksums, and Python packages are installed from frozen `uv.lock` hashes.

### Verification
1. PR #23 closed via GitHub API.
2. Production Dockerfile validated with native 2-stage build: Rust builder compiling `marketing_mcp_fast`, runtime stage enforcing `assert is_rust_accelerated()`.
3. All Super-Linter and CI gates remain green on `main`.

### Prevention rule
> **Automated AI/bot security PRs must never be merged without full container lint (Hadolint/Super-Linter) verification; cryptographic verification must reside in declarative lockfiles (`uv.lock`, `Cargo.lock`) rather than unpinned inline shell pipes.**

### Reusable lesson
Automated remediation bots often generate code that solves a narrow heuristic rule in isolation while violating broader system invariants (shell safety, package pinning, layer caching). Never auto-merge bot PRs without standard end-to-end linting and build validation.
