# Launch Closure Hardening Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Convert the current advanced-beta implementation into a release-proven public beta first, then a production-GA service, without adding unrelated statistical features.

**Architecture:** Treat launch closure as six independent hardening streams with explicit dependency order: CI/release truth, durable worker execution, production persistence, production identity, contract truth, and final release governance. Public beta is allowed only after the beta gate passes; GA remains blocked until external persistence, distributed compute, production identity, observability, backup/restore, and artifact provenance are proven.

**Tech Stack:** Python 3.12, PyMC-Marketing, MCP Python SDK 2.x, Starlette/Uvicorn, SQLite for local mode, PostgreSQL-compatible metadata target, object storage target, GitHub Actions, uv, Ruff, Pyright, pytest, Docker, CycloneDX SBOM, GitHub Releases

**Spec:** `docs/PRODUCTION-READINESS.md`

## Global Constraints

- Do not add new marketing-science capabilities until the launch-closure gate is green
- Every release claim must be backed by machine evidence from the exact candidate commit
- Public beta may use API-key authentication and single-instance persistence only if those limits are explicit in release docs
- Production GA must not depend on SQLite or local filesystem state for durable shared metadata or artifacts
- Remote HTTP must fail closed and must never fall back to the trusted stdio principal
- Decision-grade outputs remain gated by diagnostics and warning preservation
- Raw reusable API-key secrets must never be persisted in browser storage, Firestore, logs, errors, evidence, or repository files
- Release-critical GitHub Actions must be green before tag creation
- No release workflow may publish artifacts built from a different commit than the tested candidate

What still blocks release approval:

- production OAuth/JWKS identity is not wired into the active HTTP auth path
- capability truth has at least one semantic drift around iROAS decision gating
- readiness reports the job subsystem healthy without proving a worker can execute work
- release workflow does not yet prove same-SHA wheel+container plus provenance/signing
- main branch is not protected by required checks

## Launch tiers

### Tier BETA-LOCAL

Allowed when:

- local stdio smoke suite passes
- package clean-install smoke passes
- all stable capabilities referenced by the local usage guide have executable evidence

### Tier BETA-REMOTE

Allowed when all of the following are green:

- P0 CI recovery
- request-scoped auth and tenant E2E tests
- verifier-backed API-key issuance/revocation E2E tests
- worker execution path either fully functional or explicitly disabled/experimental
- exact-commit release evidence generated by CI
- Docker image built and smoke-tested from the candidate SHA
- no known credential leakage path

### Tier GA-PRODUCTION

Allowed only after:

- external production metadata adapter
- object-storage adapter
- worker/API process separation with recoverable execution
- production OAuth/JWKS integration or explicitly approved equivalent identity provider
- distributed tracing exporter and alerting integration
- backup/restore and artifact reconciliation drills
- same-SHA signed/provenanced release artifacts
- required branch protection rules
- H0-H6, G0-G5, AQG green from the exact release commit

## Master acceptance criteria

Public beta is launchable when:

- required CI actually executes and is green on the exact candidate SHA
- package and Docker smoke tests pass
- stable capability inventory matches runtime behavior
- remote API-key authentication and tenant isolation pass E2E
- no raw secret persistence path exists
- async job capability is either fully worker-backed or explicitly not presented as durable/stable
- release evidence contains hashes/digests and dependency versions

Production GA is launchable only when, in addition:

- metadata and artifacts use production external backends
- background compute is isolated from the API process
- production OAuth/JWKS identity is wired and tested
- backup/restore and reconciliation are proven
- traces/alerts are connected to production backends
- release artifacts have provenance/signing policy satisfied
- branch protection requires the release-critical checks
- G0-G5, H0-H6, AQG all reference exact-commit evidence
